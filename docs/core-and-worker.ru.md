# Ядро и воркер

[English](core-and-worker.md) | [**Русский**](core-and-worker.ru.md)

**Процесс** — lifecycle, по которому мы работаем (`Intake -> Analyze -> Specify -> Decompose -> Declare -> Implement -> Verify`). Он описан в [workflow.ru.md](./workflow.ru.md). Процесс — не runtime-роль.

На этом Процессе две runtime-роли. Их нельзя смешивать.

| Имя | English | Что это | Чем это не является |
|---|---|---|---|
| **Ядро** | Core | Машина, которая исполняет Процесс: FSM, гейты, evidence, `next`, archive, `board` | LLM. Человек, который заполняет файлы Change. Описание Процесса |
| **Воркер** | Worker | LLM **или** человек, который пишет артефакты Change текущего шага | CI/OS-джоба. Очередь работы. Human Gate. Тот, кто выбирает следующий шаг или классифицирует Red/Green |

Ядро — kernel CLI: `deltafuse next`, `evidence`, `advance` (проверка гейта + переход; `check-gate` — его read-only предпросмотр), `state`, `decide`, `archive`, `board` и `artifact write`. Оно читает git продукта и предоставляет службу сериализации Artifact Writer для атомарного обновления файлов. Оно не выдумывает claims, текст спецификации, TASK и код продукта. Оно не вызывает модель.

Воркер читает то, что разрешает шаг, и пишет только файлы этого шага. Одни и те же пути для LLM и человека. Skills (`process/skills/*/SKILL.md`) привязывают воркера к LLM. `deltafuse next --human` привязывает тот же шаг к человеку. Второго процесса «для людей» нет.

```text
Воркер  --только файлы Change-->  git продукта
Ядро    --next / evidence / advance / archive-->  git продукта
Ядро    --halt, если гейт не прошёл-->  Воркер
```

## Почему Worker — не CI worker

В этом репозитории **Worker / воркер** всегда значит исполнитель шага (`llm | human`). Это не:

- джоба GitHub Actions / очереди;
- OS worker process;
- производная очередь (`deltafuse next --list`) — её считает Ядро;
- **Human Gate**.

Если речь про джобы, очереди или merge — не говорите Worker.

## Human Gate — не воркер

**Human Gate** (DEC / accept spec / merge) — остановка в Процессе. Пройти её может только человек. Заполнить `/analyze` или `/declare` вручную — работа воркера. Принять `DEC-*` — работа Gate. Один человек, две шляпы. Ядро не auto-accept Gate. Воркер не выдаёт Gate за шаг.

Что ядро может проверить: вердикт записал `deltafuse decide`, его receipt привязан к байтам, на которые отвечали, и с тех пор их никто не менял. Кто запустил `decide`, ядро не знает. Без пароля Human Gate (`deltafuse gate-password set`) воркер, сам запустивший `decide`, проходит Gate, и его receipt говорит `human_check: none`, как и человеческий. С паролем `decide` читает его только из интерактивной консоли (`human_check: password`); но файл пароля — файл в рабочем дереве, и воркер, убравший его в сторону, снова отвечает с `human_check: none`. Смотрите `human_check` в журнале гейтов; от воркера, который правит файлы намеренно, изолируйте его на хосте.

## Чего ядро не останавливает

Ядро строится против воркера, который ошибается, а не против того, кто его атакует. Оно отказывает в том, к чему модель приходит по ошибке или пытаясь дойти до зелёного: частичный прогон тестов, запуск файла теста напрямую, ослабленный тест, ослабленный leash, расширенные пути задачи, коммит с `--no-verify`, мусорная или рукописная запись, ручная правка `coverage.yaml`. Воркер с той же оболочкой, что у человека, по-прежнему может подделать намеренно, и ядро не утверждает обратного:

- Receipts в `.deltafuse/` (переходы, журнал гейтов, receipts Artifact Writer) без ключа: сделанный вручную имеет форму записи ядра. Отодвинутый файл пароля даёт ответ на Gate с `human_check: none`.
- Изолированный прогон Red-оракула убирает `-p`, `-o addopts`, незамороженные `-c` и `PYTEST_ADDOPTS`/`PYTEST_PLUGINS`; плагин, установленный как entry point пакета, всё равно загружается.
- Чистый `git merge` не запускает `pre-commit`; удаление lock в коммите с `--no-verify` делает ветку веткой без DeltaFuse.
- Сбой окружения в Red распознаётся только по отчёту pytest; на JVM отсутствующий ресурс или `NoClassDefFoundError` читается как поведенческий сбой.
- Как раннер без отчёта отвергается только голый интерпретатор (`python <file>.py`, `python -c`); `tox`, `npm test` и подобные по-прежнему идут без отчёта. Без `workflow.test_commands` «весь набор» определяется эвристикой.
- Раннер без отчёта, который читает ядро (`npm test`, `cargo test`, `go test`), судится по коду выхода. Чтение отчётов Gradle не проверено на настоящей сборке; тестовый класс Kotlin в файле с другим именем сопоставляется, только если этот файл объявлен.
- Принятие спецификации связывает текст разделов, на которые ссылаются spec-delta и срезы, а не остальное дерево `docs/spec/**`: требование, которое никто не цитировал, после вердикта править по-прежнему можно (его судит leash при принятом baseline). Change, пропустивший Specify, сравнивается со всем деревом, каким оно было на его Intake.
- Продукт, установленный из колеса, пинит digest упакованных ассетов (`assets/manifest.json`), а не кода ядра; checkout исходников пинит и то и другое.
- Leash не перечисляет каталог, который git игнорирует целиком (`target/`, `node_modules/`, игнорируемый `__pycache__/`): записанное туда не судится. Сам `.gitignore` судится.
- Пока коммит с квитанцией `decomposed` этого Change не сделан, leash не может датировать задачу: поздно добавленную задачу тогда останавливают только Writer и проверка рукописных файлов. Squash, сводящий квитанцию и позднюю задачу в один коммит, читается как «вовремя».
- Hook не судит коммит без родителя, а также коммит или диапазон, в базе которого нет `.deltafuse/lock.yaml` (тот, что ставит DeltaFuse).
- Без пригодного базового коммита шаблон CI-leash судит только головной коммит относительно его родителя и сообщает об этом предупреждением workflow.
- В подкаталоге git-репозитория `advance` пишет `leash: checked: false` и не блокирует; `init`, `leash` и `validate-layout` такую раскладку отвергают.
- Предупреждение об отсутствующем hook (`leash`, `next`, `validate-layout`) молчит, когда задана `CI`: оболочка воркера, где она задана, ничего не услышит о клоне, коммиты которого никто не судит.
- Change, пропустивший Specify, сходится только пока `docs/spec/**` остаётся таким, каким был на его Intake, кто бы его ни изменил: правка спецификации из другого Change останавливает его, а выход — переоткрытие по gap или собственная принятая спецификация.

Страховка от всего этого — вне досягаемости воркера: CI-задача leash, ревью diff человеком и изоляция воркера на хосте.

## Сквозной режим

Точка входа LLM-воркера по умолчанию — `/run`. Воркер вызывает `deltafuse next`, загружает названный skill и продолжает в той же сессии. Человек не вставляет каждую slash-команду.

Цикл останавливается только когда:

1. `halt.kind` = `decision` — показать `halt.choices`, ждать, затем `deltafuse decide --decision …`.
2. `halt.kind` = `spec` — показать `halt.choices`, ждать, затем `deltafuse decide --spec …`.
3. Гейт упал, задача blocked, или человек выбрал inspect — стоп, осмотр, затем снова `/run` или названный шаг.

Список кнопок хоста — [контракт halt](./contracts/halt.ru.md). `deltafuse decide` записывает клик, это не auto-accept. Ядро UI не рисует. Merge и `git push` остаются Human Gate. Список записи — [конверт](./contracts/leash.ru.md): хост MUST резать write-tools по `envelope.write`. Если не умеет — `/run` всё равно зовёт `deltafuse leash` перед концом шага (не замена hook). UI fuse-map и кнопки Cursor живут вне `src/deltafuse/**` и читают [снимок доски](./contracts/board-snapshot.ru.md).

Одношаговые slash-команды остаются, чтобы после сбоя перезапустить один шаг.
