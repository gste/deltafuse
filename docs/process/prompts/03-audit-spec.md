# Prompt: audit-spec

Job prompt: **валидация спецификации и аудит ADR**. Итеративный инструмент для проверки непротиворечивости, адекватности и полноты связки `docs/init/` ↔ `docs/decisions/` ↔ `docs/spec/`, зеркалирования принятых ADR в закон и выявления скрытых развилок.

Как использовать: вставь core prompt из [`../agent-prompt.md`](../agent-prompt.md), затем этот файл. В GUI вызывается через команду `/audit-spec`.

Этот файл **не повторяет процесс**: роль, правила человеческих гейтов, формат преамбулы — в `AGENTS.md` и `docs/process/**`.

---

## 0. Preconditions

- Существуют `docs/spec/` и `docs/decisions/`.
- Роль на сессию: **Auditor / Spec editor (draft)**. Продуктовый код не пишешь, задачи в `docs/todo/` не нарезаешь.
- Принимать или отклонять ADR ты **не имеешь права** — статус `accepted` / `rejected` выставляет только человек.
- В преамбуле указывай `change type: spec-patch (audit & adr sync)` или `change type: bootstrap (spec audit)`.

## 1. Audit dimensions

### A. Аудит принятых ADR (`status: accepted`)
Для каждого принятого ADR в `docs/decisions/`:
1. **Полнота и адекватность**:
   - Чётко ли сформулирована проблема в контексте?
   - Описаны ли минимум 2 жизнеспособные альтернативы?
   - Указаны ли явные позитивные и **негативные последствия / трейд-оффы**?
   - Указан ли список затронутых якорей (`Spec Delta`)?
2. **Зеркалирование в закон (`docs/spec/`)**:
   - Проверь, что решение из ADR перенесено в соответствующий модуль `docs/spec/` **императивным текстом** (как система обязана вести себя прямо сейчас).
   - В спеке **запрещены** формулировки «см. варианты в ADR-0002» — в спеке остаётся только итоговый закон.
   - Если решение не отзеркалено — внеси правку в спеку с объявлением Spec delta.

### B. Аудит открытых развилок и генерация новых ADR
1. Сканируй все модули `docs/spec/**` на:
   - Фразы неопределённости («на усмотрение», «возможно», «в будущем», «TODO», «TBD»);
   - Двойственные варианты реализации без явного выбора;
   - Скрытые технические решения, требующие фиксации архитектурного выбора.
2. Для каждой нерешённой развилки:
   - Сгенерируй черновик `docs/decisions/NNNN-<slug>.md` с `status: proposed`.
   - В спеке пометь проблемное место якорем `OPEN DECISION` со ссылкой на черновик ADR.
   - Добавь строку в `docs/decisions/README.md`.

### C. Аудит полноты покрытия Init Requirements
1. Сверь `docs/init/**` со сводной таблицей покрытия в `docs/spec/README.md`.
2. Каждое требование Init обязано иметь однозначный статус:
   - `in scope` (с указанием конкретного модуля и якоря спеки);
   - `out of scope` (сознательно исключено из первой версии);
   - `OPEN DECISION` (вынесено в черновик ADR).

### D. Аудит Human-Gated зон
1. Проверь наличие раздела **Human-gated зоны** в `docs/spec/00-context.md` или `docs/spec/README.md`.
2. Все критические области (безопасность, токены, доверие, публичные API, разрушающие миграции БД) должны быть явно задекларированы для контроля человека при ревью.

## 2. Iterative cycle

```text
[Человек принял/отклонил ADR]
          │
          ▼
    /audit-spec
          │
          ├─► 1. Зеркалирует принятые ADR в docs/spec/
          ├─► 2. Генерирует новые ADR на найденные пробелы
          ├─► 3. Обновляет docs/spec/README.md (TOC, coverage, open decisions)
          │
          ▼
[Отчёт о готовности к переходу на spec-first]
```

## 3. Definition of Done

- [ ] Все принятые ADR (`status: accepted`) проверены на адекватность/полноту и отзеркалены в `docs/spec/` императивным текстом.
- [ ] Все нерешённые развилки в спеке оформлены как черновики ADR (`status: proposed`) и занесены в реестр `docs/decisions/README.md`.
- [ ] Таблица покрытия в `docs/spec/README.md` синхронизирована с `docs/init/` и принятыми ADR.
- [ ] Внутри `docs/spec/**` нет «висячих» ссылок на Init или «TODO» без открытых ADR.
- [ ] Статус `STATUS.md` не изменён агентом (решение о переключении на `spec-first` принимает человек).
- [ ] Сформирован чёткий отчёт: что отзеркалено, какие ADR ожидают решения человека, готова ли спека к реализации.
