# Prompt: init-requirements

Job prompt: зафиксировать замысел продукта и входящие требования в `docs/inbox/**` до появления спецификации.

Как использовать: вставь core prompt из [`../agent-prompt.md`](../agent-prompt.md), затем этот файл, затем свободный вход человека (идея, ТЗ, Confluence-выгрузка, ограничения).

В GUI агентов: вызов скилла `/init-requirements`.

---

## 0. Preconditions

- `stage: bootstrap` (или пустой `docs/spec/README.md`).
- Роль: **Init author (draft)**. Не пишет `docs/spec/**`, не открывает задачи, не пишет продуктовый код.
- Вход: свободный диалог в чате или сырой файл в `docs/inbox/`.

## 1. Existing inbox triage

Если в `docs/inbox/` уже есть файлы требований, остановись и предложи ровно три варианта:
- **A. Archive and rewrite.** Перенеси текущие файлы в `docs/archive/inbox/` и собери новые требования в `docs/inbox/` на основе диалога.
- **B. Discard and restart.** Удали старые файлы из `docs/inbox/` и начни заново.
- **C. Keep and complement.** Дополни текущие файлы в `docs/inbox/` новыми разделами.

## 2. Capture requirements

Сформируй понятный структурированный файл `docs/inbox/requirements.md` (или `<slug>.md`), фиксирующий:
- Цель продукта / фичи и бизнес-контекст;
- Пользовательские роли и ключевые сценарии;
- Входные и выходные данные;
- Архитектурные и технологические ограничения;
- Открытые вопросы и развилки для ADR.

## 3. Definition of Done

- [ ] Входящие требования сохранены в `docs/inbox/**`
- [ ] Развилки и архитектурные альтернативы выделены в явные списки для ADR
- [ ] `docs/spec/**`, `docs/todo/**` и продуктовый код не тронуты
- [ ] Коммит выполнен локально: `git add docs/inbox/ && git commit -m "docs(inbox): capture initial requirements"`

В конце ответа по-русски: путь к созданному файлу в `docs/inbox/`, краткий список зафиксированных модулей и команда для компиляции спеки (`/init-to-spec`).
