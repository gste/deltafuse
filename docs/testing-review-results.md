> Ревью: `docs/testing-strategy.md` + `docs/testing-roadmap.md` против фактического состояния репозитория (коммит `c91f9cf` + незакоммиченные правки).
> Формат: каждая секция дописывается по мере проверки (запрос пользователя — фиксировать результаты сразу после каждой проверки).

## Часть 1. Оценка самих планов (testing-strategy.md / testing-roadmap.md)

### Вердикт по адекватности: ВЫСОКАЯ, с оговорками

Ядро стратегии верное и соответствует инженерной практике для repo-инструментария такого класса:

- **Пирамида правильная**: структурные инварианты (50%) → process/FSM (25%) → E2E-реплеи (15%) → LLM evals (5–10%). Это инвертированная относительно веба, но корректная пирамида для spec-driven фреймворка, где «продукт» — это файловые артефакты и правила переходов, а не runtime-поведение. Большая база дешёвых детерминированных проверок + малое число дорогих сквозных — здраво.
- **Детерминизм как принцип** («E2E без LLM», «deterministic replays») — ключевое правильное решение: тесты процесса не должны зависеть от недетерминированной модели.
- **LLM evals вынесены в опциональный слой** и не блокируют CI — корректно.

### Сильные стороны планов

1. **Полное покрытие инвариантов proposal**: наборы 1–7 стратегии покрывают все 31 core invariant косвенно и DoD-пункты напрямую (change.yaml+immutable request, pin версии, hash-фиксация, DAG задач, coverage-цепочка CR→task→test, Red/Green gates, архивация).
2. **Соответствие фактическим проблемам репозитория**: набор 4 (hash/installer) прямо бьёт в баг пиннинга версий из Review-01; набор 1.3 (strict-mode) — в «пустышки» и расползание схем.
3. **CLI `df validate` / `check-gate` как feedback-loop для агентов** — это самый ценный элемент плана: превращает тесты из постфактум-проверки в gate, который LLM-агент вызывает перед переходом шага.
4. **Пошаговый roadmap с DoD-критериями** (roadmap) — этапы имеют границы, задачи, критерии приёмки.

### Выявленные дефекты планов

#### Д1. КРИТИЧНО: Набор 1.2 неосуществим как написан — шаблоны не валидируются схемами
`testing-strategy.md` требует: «каждый файл-шаблон в `process/templates/**` обязан на 100% валидироваться своей схемой», включая `change.yaml → change.schema.yaml`, `TASK-001-template.md → task.schema.yaml`, `SLICE-01.md → slice.schema.yaml`.
Проверка факта: `TASK-001-template.md` имеет frontmatter с `change: CHG-000-example` — **проходит** (паттерн допускает `-example`? да: `CHG-[0-9]{3,}(-[a-z0-9-]+)?`). Однако:
- `evidence/red/evidence.yaml` содержит `command: <sanitized command>` и `summary: <why this is the expected failure>` — строковые плейсхолдеры, OK для схемы (type string), **но** `exit_code: 1` + `result: expected-failure` для red — совместимо. А вот `spec_status: unchanged` — в enum. Итак evidence-шаблоны проходят.
- Но `routing.yaml` → в стратегии указана валидация routing.yaml, а в наборе 1.2 её нет (появилась схема `routing.schema.yaml` после фиксов Review-02; стратегия писалась до и не обновлена).
- `_capabilities.yaml` шаблон — `domains: {}` — проходит capability.schema (minItems нет).
Реальный дефект: **стратегия ссылается на 7 схем, а после фиксов их 9** (добавились routing, coverage, spec-delta... проверю в факте: routing, coverage, slice, spec-delta, change, capability, decision, evidence, task = 9). Roadmap этап 1 говорит «Проверка компиляции всех 7 схем: change, capability, slice, task, evidence, decision, coverage» — их 7 по списку, но факт = 9 схем (есть ещё routing и spec-delta). План устарел относительно состояния схем.

#### Д2. КРИТИЧНО: Набор 3 (FSM) противоречит фактическому state-machine.md
Стратегия §3.1 требует переход `analyzed -> specified (при наличии spec-delta.md)`. Фактическая машина состояний (docs/state-machine.md) имеет промежуточный `specification-proposed` и баг-путь `analyzed -> targeting`. Стратегия не знает о статусе `specification-proposed` (18 статусов) и о баг-пути в целом в §3.1; баг-путь упомянут в 3.3, но как `analyzed -> specified (delta: none) -> decomposed`, что по фактической таблице переходов **невозможно** (из analyzed при requirement_delta:none переход не в specified, а напрямую в decomposed-путь; фактически в state-machine.md: `analyzed → targeting (bug)` или `analyzed → specification-proposed`).
Стратегия пишет `targeting -> target-confirmed` и далее `target-confirmed -> implementing -> implemented` — совпадает. Но §3.3 «Not reproduced: переход в not-reproduced из analyzing, targeting и verifying» — в фактической таблице state-machine.md not-reproduced — терминальный статус без описанных входящих переходов (это была находка ревью proposal-сверки: «not-reproduced висит»). Стратегия тестирует переходы, которых нет в каноническом документе — тестируется не specs, а воображаемая машина.

#### Д3. СРЕДНЕ: Набор 4.1 и roadmap 2.2: несуществующие пути адаптеров
Стратегия §4.1 и roadmap 2.2 требуют «Генерация адаптеров `.agents/skills/`, `.cursor/rules/`, `.gemini/skills/`». Факт: инсталлятор генерирует `.agents/skills`, `.cursor/skills`, `.gemini/skills` (значение по умолчанию + конфигурируемо через `adapters.roots`). `.cursor/rules/` не существует нигде. План закодировал ошибку.

#### Д4. СРЕДНЕ: Набор 3.2 «Попытка перевести в implemented, если evidence.exit_code != 0» — некорректная семантика Red
Для Red-фазы `exit_code: 1` и `result: expected-failure` — это **норма**, не ошибка. Ошибка семантики: переход в `target-confirmed` требует Red (падение), а стратегия формулирует негативный гейт на `implemented` с exit_code!=0 — это относится к Green (там exit_code: 0 обязателен). Формулировка небрежна, но направление верное (Green требует 0).

#### Д5. МЕЛКО: Тесты контекстного линтера (набор 5, roadmap 5.1) не имеют источника истины
«Проверка соответствия Context Contract по таблице допустимых путей чтения» — таблица путей (Reads/Must NOT read по шагам) существует только в narrative-доках (context-model.md, proposal). Машиночитаемого контракта (какой шаг какие пути может читать) нет ни в config, ни в схемах, ни в skills. Тестировать линтер не по чему — сначала нужен machine-readable contract.

#### Д6. МЕЛКО: tiktoken как зависимость — спорно
Стратегия предлагает `tiktoken` для подсчёта токенов. Это: (а) тяжёлая зависимость для линтера; (б) привязка к BPE OpenAI, не нейтральная. Эвристика слов сама же упомянута как альтернатива — ок, но выборtiktoken в план без обоснования.

#### Д7. МЕЛКО: пропорции пирамиды (50/25/15/5-10) не суммируются в 100% ровно (105% при полном evals) — косметика.

#### Д8. СРЕДНЕ: Стратегия не покрывает важные инварианты
Не упомянуты в плане:
- Проверка иммутабельности request.md (claims не переписываются после Intake) — инвариант «Never silently rewrite» из skill intake.
- Проверка уникальности CHG-ID (не переиспользовать архивные ID) — skill intake.
- Проверка DO-NOT-EDIT маркеров и hash-валидация адаптеров против lock.yaml — это есть в validate-layout, но в python-план не перенесено (набор 4 молчит про адаптеры, кроме структуры).
- Decision acceptance-зеркалирование в spec (инвариант 12 proposal).
- `allowed_paths`/`forbidden_paths` enforcement — упомянут как scope-drift linter (5.2) через git diff — хорошо, но git-зависимость в тестах фреймворка добавляет хрупкость; лучше file-hash snapshot.

#### Д9. МЕЛКО: Roadmap Этап 2 DoD «полностью заменяет smoke-test.ps1/sh» и одновременно «обертки-заглушки для init.ps1/init.sh» — противоречие внутри этапа: то ли заменяем, то ли сохраняем совместимость. Надо выбрать одно (веха «удалить» после стабилизации).

#### Д10. МЕЛКО: «права доступа» в test_fresh_install (roadmap 2.2) — на Windows ACL-проверки бессмысленны; кроссплатформенный план должен учесть (проверка структуры достаточна, права — лишнее).

#### Д11. СРЕДНЕ: E2E-реплеи (набор 6, roadmap 4) предполагают «code fix» шаг и вызов `deltafuse archive CHG-001` — команды archive в CLI-плане этапа 3 нет (только validate/check-gate/init). Появляется она только в roadmap 4.2 как факт. Дисбаланс: команда не запланирована к реализации явно ни в одном этапе — «протекает».

### Итог по планам: 7/10
Стратегия концептуально состоятельна (пирамида, детерминизм, CLI-gates), но содержит 3 существенных дефекта (Д1, Д2, Д11 — устаревшие/невыполнимые требования, противоречащие текущим схемам и state-machine), требующих актуализации планов до/параллельно реализации. Планам не хватает процедуры синхронизации с каноническими документами (схемы/стейт-машина менялись дважды за время жизни плана).

## Часть 2. Покрытие тестами каждого этапа lifecycle

### Фактическая реализация (проверено прогоном)

Реализовано 57 тестов (43 unit/integration/e2e + 14 evals), все проходят за секунды: `tests/unit` (schemas, templates, frontmatter, graph, integrity, fsm), `tests/integration` (installer, validator CLI), `tests/e2e` (golden, noop, failure modes), `tests/evals` (dataset, runner, provider, CLI). Плюс CLI-команды `init/validate/check-gate/archive/eval` и CI-матрица (3 OS × 5 Python).

### Матрица покрытия по 7 этапам lifecycle

| Этап | Гейт в `fsm.py` | Unit | Integration | E2E | Вердикт |
|---|---|---|---|---|---|
| 1. Intake | `intake` (наличие request.md) | test_fsm | test_validator_cli | golden (step 1) | ✅ покрыт |
| 2. Route and Analyze | `analyzed` (routing+slice+coverage) | test_fsm, test_integrity | — | golden (step 2) | ✅ покрыт структурно |
| 3. Specify | `specified` (spec-delta.md) | — | — | golden (step 3) | ⚠️ только позитив |
| 4. Decompose | `decomposed` (tasks/) + DAG | test_graph | — | golden (step 4), failure_modes (циклы) | ✅ покрыт |
| 5. Target (Red) | `targeting` (evidence/red/) | — | — | golden (step 5) | ⚠️ только наличие файлов |
| 6. Implement (Green) | `implemented` (green/+regression/) | — | — | golden (step 6) | ⚠️ только наличие файлов |
| 7. Verify/Archive | `converged` (verification.md+run.yaml), archiver | — | — | golden (steps 7–8) | ✅ покрыт, включая date-префикс архива |

### Пробелы покрытия (не покрыто ни одним тестом)

1. **КРИТИЧНО — Decision Convergence Loop отсутствует полностью.** Ни один тест не создаёт `DEC-*` файл. Стратегия §3.2 требовала: «перевод в specified запрещён при неразрешённых DEC-* в proposed». В `fsm.py` проверка decisions отсутствует как код — gate `specified` на decisions не смотрит вообще. Весь механизм `blocked-on-decision` (один из 18 статусов канона) не реализован в валидаторе и не протестирован.
2. **КРИТИЧНО — Переходы статусов не проверяются.** `VALID_CHANGE_STATUSES` в fsm.py — мёртвый код, нигде не используется; нет ни одного теста «недопустимый переход» (например, `normalized → converged`). Сам список расходится с каноном: в нём нет `specification-proposed` и `blocked-on-decision` из state-machine.md. FSM как машина не тестируется — есть только гейты-по-артефактам.
3. **Терминальные пути почти не покрыты**: `rejected`, `duplicate`, `superseded` — ноль тестов. `not-reproduced` — частично: e2e пишет evidence с `result: not-reproduced`, но не закрывает Change в статус `not-reproduced` и не проверяет входящие переходы из разных состояний (стратегия §3.3 требовала из `analyzing`, `targeting`, `verifying`).
4. **Набор 5 стратегии не реализован** — Context Budget Checker и Scope Drift Linter отсутствуют (ни кода, ни тестов). Roadmap этап 5 выполнен частично: CI есть, интеграция в скиллы и контекстный линтер — нет.
5. **Набор 4.3 частично**: детерминизм hash тестируется, но тест «изменение файла в process/ меняет hash» отсутствует; нет и теста блокировки при несовпадении hash (roadmap: «Попытка запуска Change с несовпадающим хэшем»).
6. **Набор 2.3 (design_ref → accepted DEC) не реализован**: integrity.py не проверяет статус решений по ссылкам.
7. **Набор 2.2 (spec_refs → физические якоря REQ-*) не подключён**: `find_spec_anchors` существует и тестируется в unit, но `validate_change_package` его не вызывает — битые ссылки проходят (подтверждено пробой T7 ниже).
8. **Инварианты Intake не покрыты**: иммутабельность request.md (revision вместо rewrite), уникальность CHG-ID против архива — ноль тестов.
9. **Два параллельных валидатора**: shell (validate-layout.ps1/sh, с lock/config/adapters-проверками) и python (схемы/гейты) не заменяют друг друга и не тестируют друг друга; CI shell-валидаторы не запускает. Стратегия предполагала единый движок — получилось два с разной логикой.

### Вердикт по покрытию: 6/10

Хэппи-путь и структурная валидация покрыты хорошо; итеративное ядро процесса (Decision loop) и статусная согласованность — главные дыры. Этапы 5–6 покрыты неглубоко: проверяется существование YAML-файлов, но не их семантическая корректность относительно фазы.

## Часть 3. Эффективность самих тестов

### Методика

Кроме чтения кода проведена мутационная проба: 8 целенаправленных дефектов поданы в `validate_change_package` / `check_gate` / `archive_change` (временный скрипт, удалён после прогона). Результат: **7 из 8 дефектов НЕ пойманы**.

### Результаты мутационной пробы

| # | Дефект | Пойман? | Детали |
|---|---|---|---|
| T1 | Green-evidence (`phase: green`, `result: passed`) в `evidence/red/` | ❌ | gate `targeting` проходит; гейт не сверяет phase файла с каталогом — Red можно подделать зелёным артефактом |
| T2 | Red-evidence с `result: passed`, `exit_code: 0` | ❌ | gate `targeting` проходит; инвариант «Red = expected-failure» не проверяется нигде |
| T3 | Gate `converged` при task status=`pending` | ❌ | задачи никогда не переведены в verified — гейт проходит; стратегия §3.2 требовала ровно это; fsm.py не читает статусы задач |
| T4 | Evidence ссылается на несуществующую TASK-999 | ❌ | нет cross-check evidence ↔ tasks; фантомный Red/Green проходит |
| T5 | change.yaml `status: normalized` при полностью собранном пакете | ❌ | валидатор не сверяет заявленный статус с фактическим наполнением |
| T6 | CR-002 в request.md не отображён в coverage.yaml | ✅ | `validate_coverage_completeness` работает; orphan-claims тоже ловятся (test_failure_modes) |
| T7 | spec_refs → несуществующий файл/якорь | ❌ | `find_spec_anchors` не подключён к валидатору; стратегия §2.2 требовала |
| T8 | Повторная архивация того же CHG-ID в тот же день | ❌ наоборот | archiver молча **перезаписывает** архив (`shutil.rmtree` + move) — теряет историю вместо ошибки; прямой антоним инварианта архивной неизменности |

### Оценка по категориям

**Что тесты делают хорошо:**
- Схемная валидация реально строгая: strict-mode (`additionalProperties: false`) покрыт негативами (test_schemas), все шаблоны гоняются через схемы (test_templates) — набор 1 стратегии выполнен полностью (включая routing/spec-delta, появившиеся после написания плана).
- DAG-тесты корректны: линейные, ветвления, прямые и косвенные циклы — набор 2.1 выполнен.
- Installer-тесты покрывают fresh/idempotent/force/lock-hash — наборы 4.1–4.2 выполнены (проверка «прав» из roadmap разумно опущена).
- Идиома `MockChangeBuilder` (fluent, пошаговый) удачна: e2e читаются как сценарий lifecycle, шаги соответствуют гейтам.
- Всё детерминировано, быстро (<10 сек), без shell-зависимостей; CI-матрица 3 OS × 5 Python шире плана (план просил 3 OS, без версий Python).

**Что неэффективно / создаёт ложную уверенность:**
1. **Гейты этапов 5–6 — проверки существования, а не семантики** (T1–T4). Зелёный golden-flow доказывает, что builder пишет правильные файлы, а не что валидатор ловит неправильные. В тестах гейтов нет ни одного негативного случая про evidence — отказы тестируются только для DAG-циклов и orphan-claims.
2. **test_fsm.py не тестирует FSM**: 2 из 7 гейтов, один позитивный сценарий; матрица §3.1 стратегии (8 переходов) и §3.2 (3 негативных гейта) реализованы примерно на 20%.
3. **Eval-контур циркулярен**: `MockLLMProvider` генерирует пакеты по тому же шаблону, что и `change_builder` (совпадают даже magic-значения content_hash и таймстампы). CI-шаг «Run DeltaFuse Evals Benchmark» с порогом `--min-schema-compliance 100` проверяет мок против валидатора, уже покрытого pytest, — новая информация не производится. Реальные LLM-оценки (стратегия §7.1: агент через API) не реализованы; в датасете 6 кейсов вместо 10. Mock-режим сам по себе легитимен, но CI-порог 100% на моке — иллюзия защиты.
4. **Фикстуры закрепляют неверную модель данных**: `step_intake` пишет `analysis: {routing: routing.yaml, summary: analysis.md}` уже на Intake (по канону analysis заполняется после Analyze), а coverage.yaml упоминает задачи на этапе Analyze (задачи появляются только на Decompose). Тесты кодируют несинхронизированные статусы, и валидатор такое пропускает (T5).
5. **Гигиена репозитория**: `_builder.py`, `build_evals.py`, `run_setup.py`, `test_b64.txt`, `build/`, `.pytest_cache/` — мусор в корне; часть файлов уже попала в git-status как untracked. Также `tests/README.md` не обновлён — описывает только shell-скрипты, pytest-комплекс не задокументирован.
6. **CI не запускает shell smoke/validate-layout**, а roadmap-заявка «pytest полностью заменяет smoke-test» не доведена: ни обёрток-заглушек (2.2), ни удаления старых скриптов.

### Вердикт по эффективности: 5/10

Тесты отлично ловят структурный мусор (схемы, циклы, coverage) и полностью проваливают семантические инварианты процесса (фазовость evidence, статусная согласованность, целостность ссылок, архивная идемпотентность). Зелёный CI при текущем состоянии не гарантирует корректность Change-пакета.

### Приоритет доработки (по убыванию критичности)

1. Семантическая валидация evidence: `phase` ↔ каталог (`red/green/regression/verification`), `result` ↔ фаза (`red → expected-failure`; `green/regression → passed` + `exit_code: 0`), `task` ↔ существующий TASK-NNN (закрывает T1–T4).
2. Сверка состояний: `change.yaml.status` ↔ фактическое наполнение; task frontmatter `status` ↔ evidence (закрывает T3, T5).
3. Подключить `find_spec_anchors` к `validate_change_package` (закрывает T7).
4. Защита архива: отказ при существующем назначении вместо rmtree (закрывает T8).
5. Decision-gate: блокировка `specified` при незакрытых `DEC-* proposed` + тесты blocked-on-decision.
6. Негативные мутационные кейсы в гейт-тестах по образцу проведённой пробы (регрессия для будущих правок fsm.py).
7. Актуализация тестов планов (Д1–Д3) и договорённость о судьбе shell-валидаторов (Д9).
