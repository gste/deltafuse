# Small-LLM Quality Contract

[**English**](small-llm-contract.md) | [Русский](small-llm-contract.ru.md)

Нормативен для фреймворка (V3-FIX-020). История программы живёт в
`backlog/roadmap/`; этот документ — каноническая спецификация.

## Референсная рамка

- Референсный нижний класс Worker — **модель до 40B параметров суммарно**,
  dense или sparse. MoE считается по полному числу параметров, а не по
  активным: 35B-A3B внутри класса, 235B-A22B — нет.
- **Sparse вернулись в класс 2026-09-23.** Исключение держалось на одном
  наблюдении — что A3B не проходит полный цикл. На версии 3.2.0 его прошли две
  такие модели: `qwen3.6-35b-a3b` (MoE 35B/A3B) и `gemma-4-26b-a4b-it`
  (MoE 26B/A4B) дошли до `converged` с correctness 100 и T10 = 0, рядом с
  dense-референсом (`backlog/roadmap/runs-2026-09-22/README.md`). Одного
  прогона на простейшем кейсе хватает, чтобы снять запрет, который опирался на
  обратное утверждение, но не хватает, чтобы сделать любую из них референсом.
- Первая qualification model — **`qwen/qwen3.8-27b`** через OpenRouter: dense
  27B, контекст 1M, max output 32 768. Выбрана потому, что повторяет продуктовый
  случай, ради которого фреймворк и строится, — корпоративная BYOK dense ~27B.
  Вердикт по-прежнему снимается с неё: результат на любой другой модели класса —
  свидетельство о классе, а не замена референсу.
- Вторая модель на границе floor — **`qwen/qwen3-32b`**: dense 32B, контекст
  131 072, max output 16 384. Стоит на границе 40B.
- Цены в этот контракт не входят: они меняются без предупреждения. Оценки
  стоимости кампании живут рядом с qualification baseline в `backlog/roadmap/`.
- Полный вызов Worker должен помещаться в context window **128k токенов**
  (qualification window). Этот потолок идёт от продуктового ограничения, а не от
  модели: корпоративный BYOK-контур, под который строится фреймворк, ограничивает
  контекст 128k, и расширение требует отдельной заявки. Собственное окно
  референсной модели больше (1M) — расширять под него qualification window
  нельзя.
- Framework-controlled input по умолчанию ограничен **64 000 токенами и 24
  уникальными файлами** на вызов. Остаток окна — обязательный запас для
  host/system instructions, tool exchange и ответа модели.
- **Число 64 000 предварительное.** Оно сохраняет ту же пропорцию ~50 % окна,
  что была у пары 32k/16 000, и должно быть подтверждено первым
  квалификационным прогоном: эффективный контекст обычно заметно ниже
  номинального, а кросс-файловое рассуждение деградирует быстрее всего при росте
  контекста.
- **Лимит в 24 файла не масштабируется вместе с окном.** Он ограничивает
  кросс-файловое рассуждение — это когнитивный предел, а не токенный, и именно
  он деградирует первым. Повышение требует отдельного замера.

## Контракт

- Один вызов Worker решает одну capability, один artifact layer и один
  проверяемый outcome.
- `next` передаёт точные bounded reads; ни один шаг не требует загрузки всего
  репозитория, всего `docs/spec/**` или соседних Changes.
- Core выполняет routing mechanics, transition checks, diff calculation и
  evidence bookkeeping вне prompt модели.
- Receipts, manifests, полные журналы и длинные command outputs не входят в
  Worker context без явной диагностической необходимости; Core отдаёт краткое
  структурированное резюме.
- При превышении token/file бюджета работа декомпозируется. Обрезание
  обязательного контекста и молчаливое продолжение запрещены.
- **Подсчёт токенов объявляет свой режим.** Каждый вердикт по бюджету несёт
  то, чем он посчитан (`endpoint` / `heuristic` / `mixed`, и `unknown`, когда
  не посчитано ничего). Квалификационный прогон выставляет
  `DELTAFUSE_TOKENIZER_REQUIRED`, и тогда отсутствующий или не ответивший
  `DELTAFUSE_TOKENIZE_URL` — отказ, а не тихий фоллбэк на эвристику: оценка не
  может обосновывать квалификационный вердикт, а режим, различающийся между
  машинами, отравляет бенчмарк, которым меряются пороги.
- Качество измеряется disk-based bench: correctness, завершённые stages,
  retries, context tokens, уникальные файлы, выдуманные пути и envelope
  violations.
- Абсолютные численные release thresholds для v3 (T1–T8, для каждого прогона и
  для медиан) зафиксированы в
  `deltafuse-bench/qualify/thresholds.md`; прогоны выполняет
  `deltafuse-bench/qualify/qualify.py`. Ослабление любого порога — отдельный maintainer Decision
  с записью в роадмап.
