## 4. Главное

Ошибка текущего фактора = `фактор / медиана токенов-на-слово − 1`. Отрицательная
ошибка значит, что эвристика недооценивает ввод (бюджет 64 000 расходуется
быстрее, чем рассчитано), положительная — что переоценивает (место пропадает).

## 5. Выводы

1. **`en` занижается на 27 %, и главный источник — не проза, а `.jsonl`.** Все
   15 журналов прогонов попадают в `en` (для `.jsonl` суффиксного правила нет),
   их плотность 7.1–9.3 токена на слово, ошибка −82 %, и это 74–77 % всех
   токенов категории. Без `.jsonl` `en` = 1.63–1.75, ошибка −20…−26 % — то есть
   недооценка остаётся, но втрое слабее.
2. **Правило кириллицы работает как переключатель на одном символе, а не как
   определение письменности.** Файлы, которые Core метит `cyrillic`, но где
   кириллицы меньше 10 % букв (13 из 30), стоят 1.74 токена на слово — как
   обычный английский; фактор 2.2 перезаливает их примерно на +26 %. Файлы с
   долей больше 50 % стоят 2.45 — там 2.2 близок к истине. Один символ в файле
   переводит его с 1.3 на 2.2, тогда как реальная цена меняется на 1.4x.
3. **`yaml` — единственная категория с систематическим перезалётом:** 4.5 против
   3.02–3.52 по девяти семействам, то есть порядка +42 % бюджета уходит впустую
   на YAML и JSON. Побочное, но важное: один генерируемый
   `dependencies.lock.json` даёт 73 % токенов категории (до 15.4 токена на
   слово), поэтому медиана по категории устойчива, а любое токено-взвешенное
   усреднение по `yaml` — нет.
4. **`log` не измерена вообще.** 4.8 ни подтверждён, ни опровергнут: ноль
   файлов. Это дыра в доказательной базе, а не результат.
5. **Нейтральная единица: байты выигрывают только на кириллице.** Разброс
   токенов-на-слово против токенов-на-килобайт по девяти семействам: `en`
   1.093 против 1.102, `cyrillic` 1.284 против 1.173, `code` 1.231 против
   1.234, `yaml` 1.168 против 1.184. Пересчёт бюджета в байты сузил бы
   семейственный разброс примерно на 9 % только для русского текста; для кода,
   YAML и английской прозы разницы нет.

Дополнительно, для чтения чисел: `gemma3` — единственное семейство-выброс на
`code` (3.46 против 2.81–3.06 у остальных, и именно оно расширяет разброс), а
в Корпусе `mistral-tekken` — не нативный Tekken, а обычное BPE-перекодирование
из `tokenizer.json` (другого способ TASK.md не допускает); агент записал, что
byte-level покрытие полное и UNK не встречается, так что числам можно верить с
оговоркой на плотный JSON.

Перезапуск:

```bash
cd %LOCALAPPDATA%/deltafuse/calibration
venv/Scripts/python.exe <results>/calibrate.py corpus
for f in qwen3.8 qwen3 llama3 mistral-tekken deepseek-v3 glm gemma3 \
         openai-o200k openai-cl100k claude; do
  venv/Scripts/python.exe <results>/calibrate.py run --family $f
done
venv/Scripts/python.exe <results>/calibrate.py summarize
```

`samples.csv` скриптом; вручную не перенесено ни одного числа. Рабочие данные
(venv, кэш токенизаторов 107 МБ, `preflight.py`) лежат в
`%LOCALAPPDATA%/deltafuse/calibration/` и в репозитории не хранятся.
