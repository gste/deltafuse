# Fuse-Back — план работ в отдельном репозитории

План выполнения [решения уровня 1](1-DECISION.md). Работа идёт **параллельно**
роадмапу DeltaFuse: до вехи F5 она не требует ни одной правки во фреймворке.

Repository: `fuse-back` (новый, рядом с `deltafuse` и `deltafuse-bench`).

## Инварианты, которые нельзя нарушать

1. **Fuse-Back не входит в FSM DeltaFuse.** Он производит артефакты и выходит.
   DeltaFuse о нём не знает ничего.
2. **Ожидаемое поведение не выдумывается.** Утверждение теста — это результат
   запуска кода, а не предсказание модели. Модель предлагает вызов, значение
   вписывает исполнение.
3. **Работа идёт до `project.baseline: accepted`.** Характеризация после
   приёмки baseline — отдельный человеческий шаг (возврат в `draft`).
4. **Только stdlib + `pyyaml`** в детерминированном ядре; клиент модели —
   OpenAI-совместимый, как в референсном хосте.

## Вехи

| веха | что даёт | зависит от | прогоны модели |
| --- | --- | --- | --- |
| **F0** скелет репозитория | пакет `fuseback`, CLI `runner \| catalog \| characterize \| handoff`, тесты, CI | — | нет |
| **F1** обнаружение раннера | `workflow.test_commands` в `.deltafuse/config.yaml` плюс доказательство одним запуском | F0 | нет |
| **F2** скелет каталога | `docs/spec/_capabilities.yaml`: все `draft`, непересекающиеся `code_roots`, список ничейного кода; отчёт человеку | F0 | да, один проход |
| **F3** характеризация | `tests/characterization/**`, зелёные на текущем коде; правила подозрительного поведения | F1, F2 | да, основной объём |
| **F4** спека из тестов | `docs/spec/<domain>/<capability>.md`, требования `observed`, ссылка на свой тест | F3 | да, малый объём |
| **F5** передача | проверки `validate-config`, `validate-layout`, зелёный `test_commands`, отчёт с подозрительными | F4 | нет |
| **F6** бенчмарк | вторая свита в `deltafuse-bench` ([BENCH.md](BENCH.md)) | F5 | да, для замеров |

## Что делается в какой веху

**F0.** `fuseback/` (детерминированное ядро), `fuseback/model/` (клиент
эндпоинта), `fuseback/cli.py`. Формат отчётов — markdown в
`docs/intake/fuse-back/`. Прогон тестов в CI на Python 3.10–3.14, как в
DeltaFuse.

**F1.** Детектор раннера: `pyproject.toml`, `tox.ini`, `Makefile`, CI-файлы.
Один smoke-запуск, его вывод — в отчёт. Если раннера нет, Fuse-Back
останавливается: без него характеризация бессмысленна.

**F2.** Детерминированная часть: дерево импортов и каталогов, кандидаты в
группы. Модель даёт им имена и границы. На выходе — каталог, где каждый файл
принадлежит ровно одной capability либо помечен ничейным. Человек правит и
принимает (шаг 4 последовательности из решения).

**F3.** Цикл на capability: модель предлагает вызовы публичных точек входа →
исполнение записывает фактический результат → зелёные остаются, красные
отбрасываются. Детерминированные правила подозрительного: проглоченное
исключение, расхождение с именем и docstring, разные ответы двух точек входа
на один вход, недетерминированность между двумя запусками. Подозрительное
всё равно фиксируется тестом с меткой.

**F4.** Одно требование на оставшийся тест, формулировка EARS, обратная ссылка
на тест. Спека говорит, что есть, а не что должно быть.

**F5.** Приёмка: обе команды DeltaFuse проходят, `test_commands` зелёные.
Здесь же всплывают два правила каталога, которые мы отложили в DeltaFuse:
непересекающиеся `code_roots` у активных capability и остановка Change,
который маршрутизирован в `draft`-capability. **Это единственная точка, где
Fuse-Back требует правок во фреймворке.**

**F6.** По [BENCH.md](BENCH.md).

## Как это идёт параллельно

- F0–F4 полностью независимы: ни одной правки в `deltafuse`.
- Первая точка синхронизации — F5 (два правила каталога).
- Вторая — F6: пороги F1–F5 добавляются в `qualify/thresholds.md`, то есть
  бенч должен быть к тому времени стабилен.
- Модель для F2–F4 — та же, что в квалификации; клиент эндпоинта можно взять
  из `qualify.py` (он уже умеет любой OpenAI-совместимый адрес, повторы,
  учёт ожидания).

## Что решать до F2 (открыто)

1. **Язык первым.** Python. Java (как в J03) требует своего харнесса вызовов —
   это отдельная веха, не входит в F0–F6.
2. **Гранулярность capability.** Пакет, модуль или сервис? От этого зависит,
   насколько выполнимо правило непересекающихся `code_roots`.
3. **Недетерминированный код** (время, случайность, ввод-вывод): правило
   «разошлось между двумя запусками» помечает его, но не пиннит. Значит, часть
   поведения останется без характеризации; это ограничение надо объявить в
   отчёте, а не прятать.
