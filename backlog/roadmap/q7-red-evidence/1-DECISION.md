# Решение уровня 1 — что считается красным тестом

Принято 2026-09-24 по результатам прогонов
[runs-2026-09-23](../runs-2026-09-23/README.md).

## Наблюдение

Ядро определяло достоверность Red по подстрокам в логе:

```python
if "AssertionError" in log or "assert " in log or "Failed:" in log:
    return AUTHENTIC_RED_CATEGORY
return "fixture-error"
```

Один и тот же `TypeError: __init__() got an unexpected keyword argument
'penalty_seconds'` получал `behavioral-mismatch`, когда pytest печатал строку
исходника со словом `assert`, и `fixture-error`, когда не печатал. Форма
трейсбэка задаётся флагами, которые выбирает сама модель: дома команда была
`pytest tests/test_limiter.py` — эхо есть, доказательства принимались; в
изолированном контуре `python -m pytest ... -v --tb=short` — эха нет, **52
отказа из 89**.

То есть правило не было строгим или мягким. Оно было недетерминированным, а
`thresholds.md` требует детерминированного подсчёта.

Вторая половина наблюдения: никто не проверял, что позеленел **тот самый**
тест, который падал. Red нужен, чтобы показать, что тест различает изменение;
без связки с Green Red-тест с опечаткой и Green другого теста читались как
закрытая задача.

## Правило

Ядро читает собственный отчёт раннера, а не его лог. Отчёт есть у всех
раннеров, которые нас интересуют: pytest пишет JUnit XML по запросу (**флаг
добавляет ядро**, не Worker), Maven и Gradle пишут его всегда.

Формулировка одна для обеих экосистем:

> **Red достоверен, если названные тесты исполнились и ни один не прошёл.**
> Всё, что помешало исполнению — компиляция, сбор, фикстура, ноль собранных
> тестов — не Red.
>
> **Green обязан зазеленить те же тесты**, которые Red перечислил упавшими.

Нейтральная формулировка обязательна, потому что экосистемы расходятся в
значении `<error>`:

| | `<failure>` | `<error>` |
| --- | --- | --- |
| pytest | любое исключение в теле теста | сбор или фикстура: тест не исполнился |
| Surefire / Gradle | падение ассерта | любое другое исключение: тест исполнился и бросил |

Правило «`failure` принимаем, `error` отвергаем» отвергло бы канонический
джавовский красный — заглушку, бросающую `UnsupportedOperationException`.
Поэтому у каждой экосистемы свой адаптер, а правило написано в терминах
«исполнился / не исполнился».

Для раннеров без машиночитаемого отчёта остаётся прежняя эвристика; запись
доказательства показывает, каким путём получен вердикт (`tests.source`).

## Следствие для компилируемых языков

На Java тест на несуществующий метод **не компилируется**: отчёта нет вообще.
Красный там — два хода: сначала сигнатура-заглушка (производственная область,
объявляется в задаче), потом красный прогон против неё. Это записано в
контракте и в скилле declare; до сих пор процесс этой разницы не знал, хотя
целевые продукты — в основном Java.

## Фальсификаторы

1. **Доля отказов Red падает, а доля Green — нет.** Если после правки отказов
   Red стало меньше, но выросли отказы Green «не зазеленил Red-тесты» — значит
   мы переложили ту же проблему на шаг вперёд, а не решили.
2. **Правило не должно пропускать сломанный тест.** Прогон с намеренно
   сломанным Red (опечатка в имени фикстуры) обязан быть отвергнут на Red, а
   не на Green.
3. **Связка Red→Green ловит подмену.** Red на одном тесте и Green на другом
   обязаны давать отказ; если такого случая не встретится ни разу за кампанию,
   проверка бесполезна и её надо снимать, а не держать «на всякий случай».
4. **Java-маршрут проходит цикл.** Пока J03 не пройден живой моделью до
   `converged`, правило про заглушку остаётся гипотезой, проверенной только на
   наших тестах.

## Что сделано вместе с этим

- **JVM-раннеры добавлены в allowlist.** До 3.3.3 `mvn test`, `mvn -B test`,
  `./mvnw test`, `gradle test`, `./gradlew test` отвергались все до одного:
  в списке были pytest, tox, npm, cargo, go — и ни одного JVM. Java-продукт не
  мог записать ни одного доказательства, не прописав `workflow.test_commands`
  руками. Префиксное сравнение для Maven и Gradle не годится (флаги идут перед
  целью), поэтому правило другое: имя раннера плюс цель из
  `{test, verify, check, integration-test}`.
