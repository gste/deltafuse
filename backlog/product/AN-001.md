# AN-001 — Analyze: один pass за `next`, срез на каждую capability

- **Дата:** 2026-09-10
- **Статус:** `done` — `feature/2026-09-10-worker-kernel`
- **Слой:** CLI / Python API (`next`, `check-gate analyzed`), skill Analyze, канон workflow
- **Зависимости:** [WK-003](WK-003.md). Не fuse-map. Не Specify F-010.

Ядро режет Analyze так же, как Declare режет задачи: один вызов воркера = один pass. Ornith (S07/S05) не должен писать все срезы и coverage в одном промпте.

## Зачем

`call_width` пакетирует три файла, но pass `slices` всё ещё «все срезы сразу». Гейт `analyzed` принимал любой один `SLICE-01`. Routing на ornith проходит; дальше модель схлопывает dual-capability Change и читает чужой spec.

## Минимум

```text
deltafuse next --step analyze --json
```

`selected` называет `analyze_pass`: `routing` | `slice` | `coverage`.

- нет `routing.yaml` → `routing` (каталог + `request.md`, без тел spec)
- routing есть, нет среза на owning capability → `slice` + `capability` + `slice_id` + `spec_refs` из каталога
- все owning capability покрыты, нет `coverage.yaml` (или статус ещё `normalized`/`analyzing`) → `coverage`
- два среза в одном `next` не выдаются, даже при `call_width: wide`

Гейт `analyzed`: каждый distinct `primary_capability` в `routing.yaml` имеет хотя бы один `slices/SLICE-*.md` с тем же `primary_capability`. Один файл на две capability — fail.

Воркер пишет только названный pass. `check-gate --gate analyzed` — после `coverage`, не после routing.

## Не делать

- Менять порядок Specify/Decompose
- Переименовывать capability
- Тюнить промпты / extras A09
- Собирать coverage Ядром (следующий срез)
- Сужать `PHASE_CONTRACTS` envelope так, чтобы сломать Declare/Implement

## Acceptance

- Intake-only Change: `next` → `analyze_pass=routing`
- Routing с двумя capability, один slice: `analyzed` fail; `next` → вторая capability
- Два slice на две capability + coverage: `analyzed` pass
- `call_width: wide` не склеивает два slice в один work item
- `--json` не пишет дерево продукта
