# LS-004 — Hook и CI, не честное слово

- **Дата:** 2026-09-11
- **Статус:** `done`
- **Слой:** installer, `process/templates/**`, `.deltafuse/config.yaml`
- **Зависимости:** [LS-002](LS-002.md), [LS-003](LS-003.md)

CLI без вызова из git/CI — снова skills. Воркер не обязан запускать `leash`.

## Зачем

Железный поводок в consuming repo: commit/CI падают, даже если агент «забыл» ядро.

## Что сделать

- `workflow.leash`: `off` | `advisory` | `enforce` в config (схема/валидатор layout).
- Свежий `init`: **`off`**. Документ: после `project.baseline: accepted` поставить `enforce`.
- Installer в `enforce` ставит клиентский hook (pre-commit или `pre-commit` YAML — один способ, кроссплатформенно) → `deltafuse leash`. В `off` hook не ставит / снимает. В `advisory` hook зовёт leash, не валит commit.
- Шаблон GitHub Action (product-owned, `process/templates`) на PR: `deltafuse leash` + существующий pytest продукта, не pytest фреймворка.
- Канон в `docs/using.md`: per-ankh / fuse-map включают `enforce` сами.

## Не делать

- `enforce` по умолчанию на пустом pet (ломает brainstorm).
- `git push` из hook.
- Требовать GitHub; hook должен работать офлайн.

## Acceptance

`init` + `leash: off` — нет обязательного hook-fail. После переключения в `enforce` и `init --force` commit с orphan `src/` не проходит (тест installer во временном git). Advisory: hook отрабатывает, commit проходит. Шаблон workflow есть в templates и не копирует `docs/contracts/**`.
