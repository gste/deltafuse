# Реестр измеримых критериев аудита DeltaFuse

Этот документ фиксирует независимые, фальсифицируемые критерии оценки качества трёх продуктовых артефактов (спецификация, код, тесты) и процесса/ресурсов в соответствии с [планом анализа](analysis-plan.md) (пакет A01).

---

## 1. Критерии качества спецификации (SPEC)

Спецификация в DeltaFuse является единственным нормативным источником продуктовых требований (`docs/spec/**`). Она обновляется через фазы `Intake -> Route and Analyze -> Specify` и служит основанием для декомпозиции, написания тестов (Target) и реализации (Implement).

| ID | Критерий | Oracle | Метод измерения | Порог | Основание порога |
|---|---|---|---|---|---|
| **SPEC-001** | **Сохранение смысла входа (Intent Preservation)** | Двунаправленная трассируемость `request.md :: CR-*` <-> `coverage.yaml` <-> `spec-delta.md` / `docs/spec/**`. Независимый аудит соответствия требований исходным claims. | `Coverage(CR) = \|Mapped(CR)\| / \|Total(CR)\| * 100%`. Проверка инварианта: отсутствие потерянных условий пользователя и отсутствие незапрошенных требований без отдельного Decision. | 100% покрытие claims (`CR-*`); 0 искажений условий; 0 незапрошенных требований (gold-plating). | Потеря требований или их искажение на этапе Specify приводит к неверной реализации и напрасным затратам на последующих шагах. |
| **SPEC-002** | **Явное выявление и разрешение неоднозначностей (Ambiguity Resolution)** | Наличие статусов `Ambiguous` / `Capability-Gap` в `routing.yaml`; отсутствие скрытых допущений агента; создание `docs/decisions/DEC-*` в статусе `proposed` и блокировка `blocked-on-decision` до решения человека. | Стресс-тестирование на противоречивых и неполных требованиях (S04, S09, S11); аудит FSM-переходов на обязательность Human Gate при архитектурных развилках. | 0 скрытых архитектурных решений; 100% развилок зафиксированы в `DEC-*` и одобрены человеком до `specified`. | Неявные допущения LLM — главный источник скрытого дрифта архитектуры и расхождения ожиданий с реализацией. |
| **SPEC-003** | **Нормативность языка (Normative Rigor)** | Наличие нормативных модальных глаголов (RFC 2119: MUST, MUST NOT, SHOULD, MAY / ДОЛЖЕН, НЕ ДОЛЖЕН); отсутствие субъективных расплывчатых определений («быстро», «удобно», «по возможности»). | Лексический и структурный анализ текста требований в `spec-delta.md` и `docs/spec/**`. Доля формализованных предложений: `Ratio(Normative) = \|Normative\| / \|Total\| * 100%`. | 100% требований сформулированы с нормативными операторами и проверяемыми условиями. | Ненормативный язык делает спецификацию недоказуемой, препятствует формулированию строгих тестов и вызывает споры при приемке. |
| **SPEC-004** | **Проверяемость и полнота оракула (Testability & Oracle Completeness)** | Наличие для каждого требования явного воспроизводимого условия верификации (входные данные, ожидаемый выход, код ошибки, инвариант состояния), позволяющего создать падающий тест (Red) до написания кода. | Инспекция связки `requirement -> test oracle`. Доля требований с формализуемым оракулом: `Ratio(Oracle) = \|Testable\| / \|Total\| * 100%`. | 100% требований имеют воспроизводимый оракул; возможность генерации Red-теста без кода реализации. | Требование без объективного оракула невозможно протестировать на этапе Target; фаза Implement порождает самосбывающиеся (vacuous) тесты. |
| **SPEC-005** | **Навигация и каталогизация возможностей (Navigability & Traceability)** | Регистрация всех модулей спецификации в `docs/spec/_capabilities.yaml`; отсутствие битых ссылок; корректный DAG зависимостей; соответствие ограничениям контекстной модели `docs/spec/context.md`. | Валидация каталога схемой `capability.schema.yaml` (schema_version 2); проверка графа связей; замер размера контекстной выборки среза (`max_tokens` <= 16000, `max_files` <= 24). | 0 битых ссылок; 0 спецификаций вне каталога; 0 циклов в DAG; размер выборки среза строго внутри лимита контекста. | Спецификация должна загружаться небольшими изолированными порциями в ограниченное контекстное окно локальной модели. |
| **SPEC-006** | **Единственность источника истины (Single Source of Truth / Delta Semantics)** | `docs/spec/**` — единственный источник продуктовых требований. Изменения вносятся исключительно через `spec-delta.md`. Отсутствие конкурирующих спецификаций в `docs/init/**`, `docs/todo/**`, коде или тестах. | Сверка фактически применённого diff в `docs/spec/**` с утверждённым `spec-delta.md`; запуск `tests/validate-layout.ps1` и `validate-layout.sh` на отсутствие устаревших runtime-путей. | 0 расхождений между утверждённой дельтой и `docs/spec/**`; 0 альтернативных спецификаций в репозитории. | Наличие параллельных источников требований ведет к рассинхронизации документации и кода, разрушая доверие к спецификации. |
| **SPEC-007** | **Актуальность и целостность при эволюции (Evolution Integrity)** | При последовательных изменениях (`CHG-001`, `CHG-002`, ...) новые дельты спецификаций не оставляют устаревших (obsolete/dead) требований; явная фиксация операций `modify` и `remove`. | Регрессионная валидация каталога возможностей; сквозное моделирование серии изменений (S02, S05, S11); аудит ссылочной целостности архива `docs/archive/changes/**`. | 0 скрытых противоречий между версиями возможностей; 100% устаревших пунктов явно удалены/модифицированы. | Спецификация деградирует («гниёт»), если изменения только дописывают новые требования, не актуализируя и не удаляя старые. |

## 2. Критерии качества кода (CODE)

Код в DeltaFuse создаётся на фазе `Implement` строго для превращения подтверждённого падающего теста задачи (`Target`, Red) в проходящий (`Green`) без регрессий. Продуктовый код подчиняется контракту атомарной задачи `TASK-NNN.md` и спецификации `docs/spec/**`.

| ID | Критерий | Oracle | Метод измерения | Порог | Основание порога |
|---|---|---|---|---|---|
| **CODE-001** | **Соответствие принятой спецификации (Spec Compliance)** | Трассируемость `TASK-NNN.md :: spec_refs` <-> сигнатуры и логика в production code; прохождение всех assertions целевого теста задачи. | Инспекция diff задачи против требований `spec_refs`; сопоставление публичного API и контрактов с текстом спецификации. | 100% покрытие требований задачи; 0 расхождений с нормативной спецификацией. | Реализация, отклоняющаяся от спецификации, разрушает предсказуемость поведения системы и обесценивает процесс Specify. |
| **CODE-002** | **Соблюдение границ изменений (Scope & Boundary Isolation)** | Список затронутых файлов в git diff задачи; соответствие `allowed_paths` и отсутствие попаданий в `forbidden_paths` из `TASK-NNN.md`. | Автоматизированная проверка diff задачи: `Paths(Diff) ⊆ allowed_paths` и `Paths(Diff) ∩ forbidden_paths = ∅`. | 100% затронутых путей находятся внутри `allowed_paths`; 0 путей в `forbidden_paths`; 0 непредусмотренных изменений. | Нарушение границ задачи («blast radius creep») ведёт к скрытым межмодульным конфликтам, каскадным регрессиям и разрушает изоляцию контекста LLM. |
| **CODE-003** | **Отсутствие регрессий (Zero Regressions Guarantee)** | Результаты выполнения доменного регрессионного сьюта (`evidence/regression/<task-id>.yaml`) и глобального сьюта проекта (`evidence/verification/run.yaml`); статус `passed`, exit code 0. | Запуск набора регрессионных команд до и после применения изменений задачи; автоматический запрет коммита при наличии регрессий. | 0 сломанных ранее работавших тестов; 100% pass на регрессионном наборе. | Появление регрессий блокирует продвижение задачи и свидетельствует о нарушении системных инвариантов. |
| **CODE-004** | **Минимализм и неспекулятивность (Minimal Implementation)** | Соответствие объёма кода требованию удовлетворения целевого теста задачи; отсутствие недостижимого или неиспользуемого кода (dead code). | Анализ тестового покрытия изменённых строк (line coverage >= 90% для нового кода); статический анализ на неиспользуемые импорты, переменные и недостижимые ветви. | 0 спекулятивных функций/параметров «про запас»; 0 недостижимых ветвей; покрытие нового кода >= 90%. | Спекулятивный («золотой») код раздувает контекстное окно локальной модели, повышает стоимость сопровождения и скрывает дефекты. |
| **CODE-005** | **Статическая типизация и чистота контрактов (Type Safety & Static Hygiene)** | Отсутствие ошибок статического анализа (линтеры, type checker); наличие аннотаций типов во всех публичных сигнатурах и интерфейсах. | Прогон проектных инструментов статической верификации (mypy, pyright, ruff/flake8); замер доли типизированных интерфейсов: `\|Typed\| / \|Total\| * 100%`. | 0 ошибок типизации и критических предупреждений линтера; 100% аннотация публичных сигнатур. | Строгая статическая типизация позволяет локальной LLM точно оперировать интерфейсами по их заголовкам без чтения реализаций. |
| **CODE-006** | **Эксплицитность обработки ошибок (Explicit Error Handling)** | Отсутствие антипаттернов маскирования исключений (`except: pass`, catch-all без проброса или логирования); генерация специфицированных типизированных исключений. | Поиск «голых» перехватов через AST/ripgrep; сверка типов возбуждаемых ошибок с оракулом `TASK-NNN.md` (раздел Failure Modes). | 0 случаев молчаливого подавления ошибок (silent failure); 100% нештатных ситуаций генерируют документированные ошибки. | Скрытое подавление исключений маскирует сбои и приводит к труднодиагностируемым авариям на более поздних этапах. |
| **CODE-007** | **Сопровождаемость и модульность (Maintainability & Structural Quality)** | Ограниченная цикломатическая сложность функций (cyclomatic complexity <= 10); отсутствие циклических межмодульных зависимостей; соблюдение SRP. | Расчёт метрик сложности кода (mccabe / radon); проверка графа импортов на ацикличность. | Cyclomatic complexity <= 10 на функцию; 0 циклических импортов; длина функции в среднем <= 50 строк. | Сложный монолитный спагетти-код не помещается в ограниченный контекст локальной модели при последующих доработках и провоцирует галлюцинации. |
