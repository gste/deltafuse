## Описание дефекта

В результате фаззинга и тестирования граничных случаев подсистемы контекста и ссылок (`context.py`, `integrity.py`) выявлен комплекс дефектов обработки путей и данных:

### 1. Path Traversal (выход за пределы корня репозитория)
В `validate_spec_ref`:
```python
file_path = (repo_root / file_part).resolve()
if not file_path.is_file():
    return f"Referenced specification file does not exist: '{file_part}'"
```
Код делает `resolve()`, но **не проверяет**, что полученный `file_path` находится внутри `repo_root` (отсутствует `file_path.is_relative_to(repo_root)` или `repo_root in file_path.parents`).
В эксперименте ссылка вида `../outside_spec.md` успешно прошла валидацию (`err == None`), позволив легитимизировать чтение произвольных файлов за пределами репозитория.

### 2. Тихий пропуск несуществующих файлов в `estimate_files_tokens`
```python
for f in files:
    if f.is_file():
        ...
```
Если в списке файлов передан несуществующий путь (опечатка, удалённый файл, битый ref), функция просто игнорирует его (`toks = 0`) без возврата ошибки или предупреждения. Валидация бюджета возвращает успех при битых путях.

### 3. Двойной учёт при дубликатах файлов
Если в `spec_refs` или списке файлов один и тот же файл указан несколько раз (например, с разными анкорами `#REQ-01` и `#REQ-02`), `estimate_files_tokens` загружает и суммирует токены файла столько раз, сколько он встретился в списке (`toks * N`), искусственно раздувая бюджет и вызывая ложные срабатывания линтера (`Context budget exceeded`).

### 4. Аномалия длинных строк без пробелов (Huge line / Minified / Binary / Base64)
Эвристика `words = text.split()` разбивает текст исключительно по пробельным символам (`whitespace`). Файл размером 100,000 символов (например, минифицированный JSON/JS, base64-данные, дамп памяти без пробелов) воспринимается как **1 слово**, что даёт расчёт в **2 токена** вместо реальных десятков тысяч токенов.

### 5. Контроль только объявленных ссылок, а не фактического чтения
Линтер `deltafuse lint-context` и валидатор FSM проверяют исключительно список путей, декларированных в `spec_refs` фронтматтера. Реальные чтения диска агентом во время выполнения команд и навыков в рантайме никак не песочатся и не перехватываются.

## Рекомендации по устранению

1. В `validate_spec_ref` добавить строгую проверку принадлежности пути репозиторию:
   ```python
   try:
       file_path.relative_to(repo_root.resolve())
   except ValueError:
       return f"Path traversal forbidden: '{file_part}' is outside repository root"
   ```
2. В `estimate_files_tokens` выполнять дедупликацию путей (`files = list(dict.fromkeys(p.resolve() for p in files))`) и явно сообщать об отсутствующих файлах.
3. Добавить ограничение на длину токена при эвристическом подсчёте (например, `max_word_len = 20`, если слово длиннее — начислять `ceil(len(word) / 4)` токенов).

## Статус исправления

**Частично исправлено (RM-004, 2026-09-08):** `validate_spec_ref` / `validate_decision_ref` отвергают путь вне `repo_root`; `validate_context_budget` сообщает об отсутствующих файлах и traversal, токены дедуплицируются. Эвристика длинных слов без пробелов (п.3) и runtime-песочница чтений агента (п.5) **не** входили в RM-004.
