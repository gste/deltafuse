# F-001: Shell-скрипты получают CRLF при checkout на Windows из-за отсутствия .gitattributes

- **ID:** F-001
- **Тип:** defect
- **Затронутый критерий:** BASE-005 (Bash smoke и layout), AGENTS.md (требование запуска `tests/smoke-test.sh`)
- **Ревизия обнаружения:** `60ea40438b0142797848356c660ab88286565e7d` (HEAD: `d9ca00f40d42171120f3e6c0cbe27ef48ae5bb9a`)
- **Точные ссылки:**
  - `tests/smoke-test.sh:3` (`set -euo pipefail`)
  - `tests/validate-layout.sh:2` (`set -euo pipefail`)
  - `scripts/init.sh:3` (`set -euo pipefail`)
  - Отсутствие `.gitattributes` в корне репозитория

## Ожидаемое и наблюдаемое

- **Ожидаемое:** Согласно AGENTS.md, перед сдачей изменений выполняются проверки `tests/smoke-test.ps1` и `tests/smoke-test.sh`. В окружении Windows с установленным WSL/Bash запуск `bash tests/smoke-test.sh` должен успешно исполнять скрипт.
- **Наблюдаемое:** В репозитории отсутствует файл `.gitattributes`. При стандартной конфигурации Git на Windows (`core.autocrlf = true`) текстовые файлы при checkout получают окончания строк CRLF (`\r\n`). При попытке запуска `bash tests/smoke-test.sh` в WSL2 Bash завершается с ошибкой `tests/smoke-test.sh: line 3: set: pipefail\r: invalid option name` (exit code 2).
- **Дополнительное наблюдение по хешированию:** Функция `framework_hash` в `scripts/init.sh` вычисляет SHA-256 файлов как есть. Если файлы содержат CRLF (checkout Windows), хеш содержимого фреймворка отличается от хеша тех же файлов с LF (чистый Linux или git archive с `core.autocrlf=false`):
  - Windows (CRLF): `sha256:64b3cdb786e23c4233cdc92a84ebbae4966fb72abe49c08b5675b7a76b85119f`
  - Linux (LF): `sha256:f1c2298ce5dbabacdefa0e700ad84770a4d80ddc031e2dcb12d87fe2c3a55f56`
  Это делает lock-файл и проверку layout кросс-платформенно чувствительными к line endings.

## Минимальное воспроизведение

В среде Windows с Git (`core.autocrlf=true`) и WSL:
```powershell
bash tests/smoke-test.sh
```
Результат:
```text
tests/smoke-test.sh: line 3: set: pipefail
: invalid option name
```
Exit code: 2. Лог зафиксирован в [smoke-crlf-fail-1.txt](../analysis/experiments/A00-05/smoke-crlf-fail-1.txt).

При этом запуск того же скрипта из tar-архива, созданного с явным `-c core.autocrlf=false` (LF окончания строк), проходит успешно с exit code 0 ([smoke-1.txt](../analysis/experiments/A00-05/smoke-1.txt)).

## Влияние

- Разработчики и CI-агенты на Windows не могут напрямую выполнять bash-проверку из рабочего дерева через WSL/Git Bash.
- Различие хеша содержимого между CRLF и LF нарушает переносимость `.deltafuse/lock.yaml` между Windows и Linux разработчиками одного продукта.

## Уверенность

Высокая. Воспроизведено и экспериментально подтверждено в A00-05 на Windows 11 / Ubuntu 24.04 WSL2.

## Статус исправления

**Исправлено (RM-001, 2026-09-08):** в корне репозитория добавлен `.gitattributes` (`* text=auto eol=lf`, `*.sh text eol=lf`, `*.ps1 text eol=crlf`). Нормализация SHA в `framework_hash` не входила в минимум RM-001.

## Варианты исправления

1. **Рекомендуемый (полный):**
   Добавить `.gitattributes` в корень репозитория:
   ```gitattributes
   * text=auto eol=lf
   *.sh text eol=lf
   *.ps1 text eol=crlf
   ```
   В `scripts/init.sh` и `scripts/init.ps1` при расчёте `framework_hash` нормализовать line endings (стрипать `\r`) перед вычислением SHA-256 файлов, либо вычислять хеш нормализованного байтового потока.
2. **Более простой (минимальный):**
   Добавить `.gitattributes` со строкой `*.sh text eol=lf`.

## Стоимость контекста и сопровождения

Нулевая. Один статический конфигурационный файл `.gitattributes`.

## Способ будущей проверки

Запуск `tests/smoke-test.sh` в WSL на свежем git clone под Windows без дополнительных ручных конверсий строк (`dos2unix`).
