## Q-001 — Ширина борозды как профиль, не хардкод skill

- **Дата:** 2026-09-06
- **Источник:** A09-01a/b калибровка ornith; обсуждение 14B vs 27B+
- **Критерии:** `PROC-004`, `PROC-007`
- **Статус:** `accept`
- **Слой:** lock / schema / FSM (подшаги Analyze); **не** копия skill на модель
- **Приоритет-кандидат:** P2 (после P0 F-010 и P1 F-002)

**Вопрос.** Должен ли DeltaFuse явно регулировать, сколько артефактов пишет один LLM-вызов (узкая / средняя / широкая борозда), отдельно от бюджета чтения `context.max_tokens` / `max_files`?

**Наблюдение.** В docs борозда заявлена (`context_budget` слайса, 16000/24). В runtime не крутится: skill Analyze всё равно требует `routing.yaml` + slices + `coverage.yaml` + `analysis.md` одним ходом. У задачи нет `context_budget` ([F-002](../../findings/F-002.md)). Спас A09 харнесс `A09_ANALYZE_FOCUS=routing|slices|coverage`, не контракт фреймворка. Для ornith/14B узкая борозда нужна; для 27B+ три RTT слегка избыточны, не вредны. A11-03: BMAD выбирает ceremony **после** расследования (`bmad-build` light vs full plan) — полезно как идея профиля, не как снятие FSM-гейтов.

**Черновик направления.** Профиль ширины *вызова* в конфиге продукта/lock (`narrow` / `medium` / `wide`): один артефакт; фаза целиком; фронтир пакует Analyze сам. FSM уже пофазовый; нужны **подшаги внутри фазы** и правило «не закрывай `analyzed`, пока нет routing+slices+coverage», без требования одного ответа. Не копировать skills под каждую модель. Опционально короткие policy-флаги lock (из Q-007): не auto-accept DEC — уже FSM, не дублировать промптом.

**Вердикт A12-04.** **accept.** Минимальный вариант: `analyzed` только при полном комплекте артефактов; split записи — opt-in lock, default не обязан быть трёхшаговым. Оверфит: вшить калибровку ornith как единственный Analyze. Проверка: S02 holdout без extras закрывает routing затем slices; wide-профиль на той же фикстуре может одним шагом. Не дублирует F-002 (enforcement чтения/budget).

**Не делать.** Не вшивать ornith-сплит как единственный режим Analyze. Не снимать гейты для tiny (BM-01).

## Q-002 — Счётчик токенов = tokenizer SUT + калибровка endpoint

- **Дата:** 2026-09-06
- **Источник:** [F-003](../../findings/F-003.md), [A03-01](../packets/A03-01.md); обсуждение калибровки под LLM пользователя
- **Критерии:** `PROC-004`, `PROC-007`
- **Статус:** `implemented` (RM-003, 2026-09-09)
- **Слой:** `context.py` / CLI; optional lock pin tokenizer
- **Приоритет-кандидат:** P1 **как способ закрыть F-003**, не отдельная строка дефекта

**Вопрос.** Чем заменить `words * 1.3` так, чтобы бюджет контекста совпадал с токенами той модели, которой пользуется продукт?

**Наблюдение.** A03-01: EN 0%; RU −37.8%; код −51.9%; YAML −70.4% vs `/tokenize`. Эвристика даёт ложный pass при 16k.

**Черновик направления.**

1. Adapter к tokenizer пользователя: `POST /tokenize` (llama-server / Studio) или офлайн vocab GGUF/`tokenizers`.
2. Разовая калибровка при пине модели (`deltafuse calibrate` или шаг lock): фикстуры skill+schema+слайс → профиль: vocab/id, overhead ChatML, размер skill, резерв ответа, запас reasoning.
3. Фолбэк без эндпоинта: коэффициенты по типу файла из F-003 (`.yaml`×4, код×2.7, кириллица×2.2), консервативно.
4. Лестница prefilla калибруется отдельно (Q-001).

**Вердикт A12-04.** **accept** метод фикса F-003. Минимальный вариант: консервативный фолбэк по типу файла (п.3) + вызов `/tokenize`, если endpoint есть. Калибровка CLI — можно вторым шагом. Проверка: те же фикстуры A03-01, оценка ≥ реальных токенов (upper bound), не занижение. Не считать токены генерацией LLM.

**Не делать.** Не подменять tokenizer эмбеддингами (Q-003). Не второй finding рядом с F-003.

## Q-008 — Сверка spec-delta с live spec после Verify, не перенос SSOT на archive
