# Порядок исполнения карточек анализа

Эта очередь относится к аудиту самого фреймворка. Она не является продуктовым Change, generated skill или runtime-статусом DeltaFuse. Нормативный источник — [план анализа](../analysis-plan.md); канонические контракты остаются в `docs/**`.

## Карточка и контекст

- Читать выбранную карточку, её секцию плана, этот порядок и компактные handoff зависимостей. Входы карточки указывают пути от корня репозитория и нужные секции/символы; сначала найти их заголовки/строки через `rg -n`, затем читать только нужный фрагмент. Зафиксировать фактически прочитанные диапазоны и ревизию в manifest.
- Пути результатов предыдущих задач — будущие входы, а не утверждение об уже существующих файлах. Отсутствующий обязательный вход нельзя заменять выдуманным результатом.
- Рабочий лимит до калибровки A03: **6000 токенов полного входа + 2000 резерва ответа** на вызов. Это предварительная организационная величина. Полный вход включает system, skill, инструкции, карточку, handoff, excerpts, историю и tool results. Проверять фактическим tokenizer; если измерение недоступно, бюджет не считается подтверждённым.
- Применять меньший из рабочего лимита и измеренного лимита профиля A03. До отправки проверять, что вход вместе с резервом помещается в настроенное окно модели. Не усекать существенный текст и не обходить лимит дополнительными чтениями.
- Для дополнительных чтений разрешены только точные определения символов/refs из входа и первичные доказательства из handoff зависимостей. Каждый дополнительный путь, секцию и причину записывать в manifest. Расширение области исследования требует отдельной карточки.
- Если один вопрос или сценарий не помещается, **до его исполнения** добавить дочерние карточки `Axx-NNa`, `Axx-NNb` с конкретными inputs, зависимостями и результатом, обновить индекс. Родитель завершается после их сверки. Семейства вариантов и повторы выполнять отдельными вызовами; одна сессия не должна содержать всю группу.
- Выход вызова — до 2000 токенов, handoff — до 400 токенов. Большие логи хранятся файлами; их объём не скрывает стоимость прочитанного моделью текста.

## Доказательства и завершение

До запуска зафиксировать проверяемую гипотезу и альтернативу из карточки на конкретном инварианте/case, а также критерий из A01 (если он уже определён). Для подготовительных задач успех означает воспроизводимость входов и полноту протокола, а не соответствие фреймворка.

По мере исполнения создавать `experiments/<ID>/manifest.yaml`, `result.md` и нужные команды/логи. Manifest содержит task ID, framework revision/dirty state, входные файлы/диапазоны/hash, метод, profile ID при LLM-вызове, команды/параметры, бюджеты, выходные пути и дату. Сохранять exit code реального процесса; недоступный показатель отмечать как неизвестный. Не сохранять секреты, credentials и привязанные к машине абсолютные пути: использовать относительные пути и обозначения корней. Точные модельные источники/hash сохранять без локальных путей пользователя.

В `result.md` записать ожидаемое и наблюдаемое, verdict, уверенность, ограничения и ссылки на первичное evidence. Verdict: `pass`, `fail`, `partial`, `not-tested`, `not-applicable` с обоснованием. Непроверенная гарантия не получает `pass`. Находки оформлять как `findings/F-NNN.md` по формату плана; положительные результаты также сохранять. Общие baseline/criteria/matrices пополнять компактными строками с устойчивыми IDs.

Карточка `done` означает завершённую проверку или подготовку, **не положительный verdict**. Если отсутствует обязательный доступ/вход, записать `blocked`, причину и условие разблокирования. Платформенную проверку допустимо закончить с `not-tested` и точной причиной, как разрешает A00. Отсутствующий реальный LLM-прогон остаётся `blocked`; статические независимые задачи можно продолжать. Финальный синтез может зафиксировать такие пробелы по разрешению A12, явно ограничив вывод и не выдавая заблокированные задачи за выполненные.

## Очередь и передача работы

[Индекс](index.md) — единственный источник статусов и следующей задачи анализа. Не создавать отдельный файл глобального process status. В карточках статус не дублируется.

1. Взять указанную следующую задачу; убедиться в готовности зависимостей по handoff.
2. В индексе установить `in-progress` и текущую задачу.
3. Выполнить ограниченную проверку, записать result и handoff: вывод, IDs критериев/инвариантов/claims, evidence, нерешённые вопросы и пригодность результата для зависимых задач.
4. Обновить строку индекса, счётчики и поле следующей задачи. По умолчанию выбирать первую `planned` с разрешёнными зависимостями; при блокировке выбрать независимую готовую задачу.
5. При завершении очереди указать «Следующая задача: нет», при полной блокировке — причину и необходимое действие. История чата не является входом.

Приоритет старта: A00 → A01 → A02-01 → A03. Остальные контракты A02 можно продолжить после A03; при аппаратной блокировке — без неё. Для будущих источников в A11 проверить актуальные первичные страницы во время выполнения, не считать ссылки плана результатами исследования.

## Реальные LLM-эксперименты

Выбран пользователем `ornith-1.5-35b-a3b`. Исторический снимок A03-03 — LM Studio `:1234`. **Текущий SUT A09:** голый llama-server `:1240`, `--reasoning off`, `--cpu-moe` — [local-runtime](experiments/local-runtime/README.md). Не подменять модель, не считать mock её результатом, не объявлять 8 GB достаточными по названию A3B, не ходить в Studio-прокси.

A03-04 — отдельный анализ контракта фреймворка локальной моделью. A08-01 проверяет средство исполнения, A09 — качество полного workflow на тестовых продуктах. Эти три результата нельзя подменять друг другом. Runtime-тюнинг (кролики/медведи) закрыт; продолжать A09-01b, не новую очередь оптимизации.

До LLM-вызова подтвердить `GET http://127.0.0.1:1240/v1/models`. При недоступности не переходить на облачный provider. Сохранять request/response, prompt, параметры sampling/seed (если поддерживается), фактические input/output tokens и конфигурацию. Ответ модели — гипотеза до независимой проверки по источнику/контрпримеру.

Для A09 по каждой фазе сохранять tokens, максимум заполнения контекста, RAM/VRAM peaks, TTFT и полное время, calls/retries, overflow, ручные вмешательства и потери claims; по продукту — независимые acceptance/regression, нарушения spec, полезность тестов и актуальность документации. Отсутствующая телеметрия помечается явно. Первый проход, исправления, неуспешные попытки и причины остановки сохраняются раздельно. Минимум пилота — три повтора на case/config; малый пилот не даёт сильных статистических выводов. Analyze калибровать с `routing.yaml` первым шагом.

Подготовка этой очереди не запускает сам аудит или изменение контрактов. Предложения исправлений идут в A12 и принимаются отдельно.
