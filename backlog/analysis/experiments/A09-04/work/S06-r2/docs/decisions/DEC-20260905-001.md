## Context

The alerting subsystem (CR-005, CR-006) requires a concrete, testable definition of the sliding 60-second rejection window and the alert payload. The intake sample log is provided "for analysis" only (CR-008) and contains no expected outputs. CR-010 confirms acceptance criteria and the precise alerting API are unspecified.

## Decision

The following normative definitions are required before the spec can be gated as specified:

1. **Window semantics:** the 60-second window is a trailing sliding window evaluated per key on each `consume` event; `window_start` = latest rejection timestamp minus 60s, `window_end` = current event timestamp.
2. **Threshold:** default 100 rejections; `rejection_count` counts rejections within the window.
3. **Alert payload:** `key`, `window_start`, `window_end`, `rejection_count`, `threshold`.

## Consequences

Until a human confirms these definitions, the alerting slice cannot be fully specified. The audit-log slice (CR-003, CR-004) is independently specifiable and does not depend on this decision.
