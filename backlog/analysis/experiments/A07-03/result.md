## Ожидаемое поведение

1. **Проблема валидации тестов продукта**:
   - В отличие от тестов самого фреймворка, продуктовые тесты создаются агентом на шаге Target (`target-task`) и исполняются на шагах Implement (`implement-task`) и Verify (`verify-change`).
   - Номинальный code coverage (покрытие строк) не гарантирует качество теста: LLM может сгенерировать самосбывающийся тест (vacuous assertion, `assert True`), тест с хрупкой привязкой к приватным методам или тест, не замечающий нарушений требований спецификации.
2. **Требования к оракулу полезности продуктовых тестов**:
   - Формализовать объективный, воспроизводимый протокол оценки качества сгенерированных продуктовых тестов без необходимости участия человека.
   - Оракул должен оценивать:
     1. **Fault Injection**: падение при намеренном нарушении спецификации (мутация логики требований).
     2. **Refactoring Invariance**: прохождение при эквивалентном рефакторинге (переименование локальных переменных, извлечение подфункций, оптимизация алгоритма).
     3. **Scope Bounding**: изоляция диффа тестов рамками `TASK-NNN.md :: allowed_paths`.
     4. **Regression Guard**: обнаружение поломок смежных модулей через `evidence/regression/<task-id>.yaml`.

## Наблюдаемое поведение и спецификация протокола

Сформирован 4-мерный протокол оценки полезности продуктовых тестов (подлежит автоматическому исполнению на синтетических сценариях в пакетах A08 и реальных замерах в A09):

### 1. Измерение Fault Detection Rate (FDR)
- **Метод**: Мутационная инъекция дефектов в продуктовый код, созданный на шаге Implement:
  - Мутация M1 (Condition Inversion): инверсия граничных условий (`>` на `<=`, `==` на `!=`).
  - Мутация M2 (Off-by-one): смещение индексов или границ срезов.
  - Мутация M3 (State Transition Bypass): пропуск обязательного обновления статуса или записи в хранилище.
  - Мутация M4 (Security / Traversal): передача `../` или вредоносного payload.
- **Метрика**: $\text{Mutation Score} = \frac{|\text{Killed Mutants}|}{|\text{Total Mutants}|} \ge 90\%$.
- **Поведение**: Если целевой тест задачи проходит на намеренно сломанном коде — тест признаётся фиктивным (`vacuous`).

### 2. Измерение Refactoring Resilience Rate (RRR)
- **Метод**: Применение семантически эквивалентных трансформаций к коду реализации:
  - Замена циклов на list comprehension / map.
  - Декомпозиция метода на 2 приватные подфункции (`_helper`).
  - Замена внутреннего формата локальной структуры данных (например, `list` на `dict`).
- **Метрика**: $\text{False Alarm Rate} = \frac{|\text{False Alarms}|}{|\text{Total Runs}|} == 0\%$.
- **Поведение**: Тест должен опираться строго на публичный интерфейс модуля (`TEST-002`). Любое падение при эквивалентном рефакторинге свидетельствует о хрупкости теста (tight coupling).

### 3. Верификация Red Authenticity (TDD Oracle)
- **Метод**: Сверка содержимого `evidence/red/<task-id>.yaml` со статусом git-дерева до коммита кода реализации:
  - Дифф продакшн-кода пуст (`git diff -- src/` пуст).
  - Тест завершается с `exit_code != 0` и `result: expected-failure`.
  - Причина падения относится к `behavioral-mismatch` (а не к `ImportError`, синтаксической ошибке или сбою тестового фреймворка).

### 4. Контроль регрессий и ограничение скоупа
- **Метод**: Проверка совпадения затронутых путей с `allowed_paths` задачи и отсутствие путей из `forbidden_paths`.
- **Метрика**: `Zero Regression Guarantee`: `evidence/regression/<task-id>.yaml` содержит `exit_code: 0`, `result: passed`.
