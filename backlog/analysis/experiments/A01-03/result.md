# A01-03 — Критерии полезности тестов

**Verdict: `pass` для TEST-001..TEST-006.** На ревизии `60ea40438b0142797848356c660ab88286565e7d` (рабочий HEAD `68d3bdfa37a911eb394b9f64db2a2b0c39f155c8`) в нормативном документе [backlog/criteria.md](../../../criteria.md) формализовано дерево независимых, фальсифицируемых критериев полезности тестов в рамках пакета A01 [плана анализа](../../analysis-plan.md).

Для каждого критерия зафиксированы:
1. Уникальный ID и наименование;
2. Объективный оракул (наблюдаемый инвариант / артефакт);
3. Воспроизводимый метод измерения / верификации;
4. Строгий числовой или логический порог;
5. Инженерное обоснование порога на основе стратегии тестирования DeltaFuse (`docs/testing-strategy.md`).

| ID | Критерий | Oracle | Метод измерения | Порог | Основание |
|---|---|---|---|---|---|
| **TEST-001** | Обнаружение реальных нарушений требований (Fault Detection Power) | Падение теста (`exit_code != 0`, `AssertionError`) при искусственном внесении дефектов в логику | Мутационный анализ: `MutationScore = |Killed_Mutants| / |Total_Mutants| * 100%`; инъекция дефектов | Mutation score >= 90% для специфицированных контрактов; 100% отлов мутаций FSM/схем | «Самосбывающиеся» пустые тесты создают ложную уверенность и пропускают баги |
| **TEST-002** | Независимость оракула от реализации (Oracle Independence / Black-Box) | Ассерты проверяют наблюдаемый публичный контракт (выходы, ошибки, состояние), а не приватные детали | Статический аудит: отсутствие обращений к приватным символам (`_private`); ограничение моков | 0 обращений к приватным атрибутам; мокирование только внешних I/O границ | Привязка теста к приватным деталям ломает тесты при рефакторинге без изменения поведения |
| **TEST-003** | Устойчивость к рефакторингу (Refactoring Resilience / Low False Alarms) | При эквивалентном внутреннем рефакторинге без изменения контракта все тесты остаются зелёными | Прогон сьюта на эквивалентных трансформациях кода; замер доли ложных срабатываний | 0 ложных падений при эквивалентном рефакторинге; 100% стабильность на контракте | Хрупкие тесты парализуют рефакторинг и вынуждают агентов тратить ресурсы на переписывание тестов |
| **TEST-004** | Достоверность и специфичность Red-фазы (TDD Red Authenticity) | На этапе Target тест падает строго по причине отсутствия функционала (`behavioral-mismatch`) | Валидация `evidence/red/<task-id>.yaml` схемой `evidence.schema.yaml`: `exit_code != 0`, `behavioral-mismatch` | 100% Red-тестов падают исключительно на assertions; 0 инфраструктурных падений | Падение из-за `ImportError` или опечатки в фикстуре не доказывает готовность тестового оракула |
| **TEST-005** | Детерминизм и изоляция (Determinism & Flakiness Freedom) | Результат идентичен при N повторах подряд в любом порядке и на поддерживаемых платформах | Многократный запуск (`pytest -n auto --count=10` / `pytest-randomly`); проверка `tmp_path` | 0 flaky тестов при 10 повторах; 0 утечек состояния между тестами | Недетерминированные тесты разрушают автоматические агентные циклы и вызывают ложные сбои в CI |
| **TEST-006** | Скорость выполнения и стоимость поддержки (Latency & Maintainability) | Unit test <= 100 мс; domain regression <= 5 с; полный сьют pytest <= 30 с; компактность | Профилирование длительности (`pytest --durations=10`); запрет `time.sleep()`; test-to-code ratio <= 2.0 | Unit test <= 100 ms; domain suite <= 5 s; full pytest suite <= 30 s; 0 вызовов `time.sleep()` | Медленные тесты затягивают feedback loop, вызывают таймауты LLM и стимулируют пропуск проверок |

Полное описание критериев приведено в [backlog/criteria.md](../../../criteria.md).
