Базовые параметры профиля: загруженный контекст модели = **33,024 токена**, порог `max_tokens` в конфигурации пакета = **16,000 токенов**, резерв на генерацию и reasoning = **2,000–4,000 токенов**.

## 2. Анализ критических стресс-точек (Stress Points)

### Стресс-точка 1: Огромный сырой ввод (Big Raw Input) до Intake
- **Сценарий:** Пользователь подаёт дамп логов сбоя на 500 КБ (~150,000 токенов) или многостраничный документ требований.
- **Ограничение:** Локальная модель с окном 33,024 токенов и лимитом входа 6,000 токенов аварийно переполнится.
- **Механизм bounded execution:**
  - Вход должен фильтроваться на пред-шаге (выделение stacktrace, удаление дублирующихся строк логов).
  - Нормализация проводится порциями: raw text разбивается на логические секции, по каждой из которых извлекаются `CR-*`.

### Стресс-точка 2: Каталог больше контекстного окна (`_capabilities.yaml` > 32K токенов)
- **Сценарий:** Зрелый продукт с сотнями микросервисов и капабилити.
- **Ограничение:** Pass A фазы Route & Analyze не может загрузить весь каталог `_capabilities.yaml`.
- **Механизм bounded execution:**
  - Иерархическая организация каталога: `_capabilities.yaml` содержит только высокоуровневые домены (L1), а детальные спецификации капабилити хранятся в подкаталогах `docs/spec/<domain>/_capabilities.yaml`.
  - Векторный/семантический пре-поиск или пре-роутинг по доменам.

### Стресс-точка 3: Одна большая капабилити (Large Capability / Monolith Spec)
- **Сценарий:** Спецификация одного сложного компонента занимает 80 КБ текста (~25,000 токенов BPE).
- **Ограничение:** Фазы Specify и Decompose не могут загрузить модуль спецификации целиком без вытеснения резерва ответа.
- **Механизм bounded execution:**
  - Обязательное секционирование спецификаций через якоря `#REQ-*` и подразделы.
  - Агент читает не файл целиком, а только секции, затронутые `spec_refs` конкретного среза `SLICE-NN.md`.

### Стресс-точка 4: Длинная история архитектурных решений (`docs/decisions/*`)
- **Сценарий:** В проекте принято 50+ решений `DEC-*`.
- **Ограничение:** Загрузка всех решений в контекст Specify/Analyze переполняет окно.
- **Механизм bounded execution:**
  - Запрет чтения каталога `docs/decisions/` целиком.
  - Агент загружает только те `DEC-*`, которые явно указаны в `design_ref` среза или задачи.

### Стресс-точка 5: Циклические зависимости и разрастание графа задач
- **Сценарий:** Ошибочная декомпозиция создаёт цикл `TASK-01 -> TASK-02 -> TASK-01` или веер из 100+ связанных задач.
- **Механизм bounded execution:**
  - FSM-проверка топологической сортировки (Kahn algorithm) мгновенно отклоняет пакет с циклом на гейте `G3_DECOMPOSE`.
  - Ограничение на размер пакета изменений: если число задач > 15–20, Change-пакет обязан быть разделен на несколько независимых `CHG-*`.

### Стресс-точка 6: Разрастание матрицы покрытия (`coverage.yaml`)
- **Сценарий:** Сквозная матрица на сотни требований и задач.
- **Механизм bounded execution:**
  - `coverage.yaml` валидируется схемой построчно; для каждого `CR-*` проверяется наличие ссылки на `slice` и `task`.
  - Модель не агрегирует всю матрицу в prompt: валидация покрытия выполняется детерминированным Python-скриптом CLI (`deltafuse validate`), разгружая LLM.

### Стресс-точка 7: Global Reconciliation и финальная фаза Verify
- **Сценарий:** Проверка целостности всего репозитория после слияния десятков задач.
- **Механизм bounded execution:**
  - Модели **запрещается** читать полный git diff проекта.
  - Верификация выполняется на основе агрегированных машиночитаемых отчётов: JUnit XML / pytest JSON лог, отчет `deltafuse validate` и файл `coverage.yaml`.
  - Модель формулирует финальный отчёт `verification.md` исключительно на основе метаданных и статусов выполнения тестов.
